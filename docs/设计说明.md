# 漂流岛屿（drift-islands）设计说明 v0.1（讨论稿）

## 0. 一句话

末世海上漂流**纯文字聊天室**游戏：玩家开船在坐标海上游荡，遭遇玩家创建的岛屿，收集资源升级船只，可驻扎建基地；怪物随时间变强并主动攻击人类；世界演变由 AI 推进。

**为什么是纯文字**：带画面的游戏开发难度太大（3D 美术、每个物件的真实行为几乎无法逐个实现）。纯文字去掉画面成本，内容由 AI 生成；玩家造岛的门槛从“会用编辑器”降到“会打字”。

## 1. 为什么做这个（机会）

- **广告验证了需求**：抖音、番茄小说上末世海上重建的广告很火，但广告与实际游戏完全无关——需求存在、供给缺位。把广告里那个游戏真做出来，第一波流量就是白捡的。
- **同类产品是固定路线**：游戏平台上已有的 2D 末世海上重建游戏走固定科技升级路线；本项目用**玩家扩充地图 + AI 演变世界**做差异化。
- **参考蛋仔派对**：蛋仔工坊证明了“内置编辑器 + 乐园分发 + 创作者激励”能跑出规模（5000 万创作者、2 亿张地图）；本项目把“地图”换成“岛屿”，把“乐园”换成“同一片海”。

## 2. 核心循环

造岛（定规则 + 资源方向）→ 开船（选方向 / 随机漂流）→ 遭遇岛屿 → 探索收集 → 升级船只 / 驻扎建基地 → 怪物变强施压 → 再出海

## 3. 世界结构

- **坐标海**：二维坐标网格，每格是一片海域；一座岛占据一个坐标。
- **岛屿**（玩家创建）：名字、坐标、规则（自然语言 3–5 条）、资源方向（大类，如燃料、零件、科技件）；岛上的怪物、遗留科技、具体细节由 AI 按规则细化。
- **聊天室**：所有玩家都在公共海频道；进入岛屿后生成岛屿子频道，仅岛内玩家可见；离开岛屿回到海频道。
- **移动**：每步选择方向（东 / 南 / 西 / 北）或随机漂流。
- **跟踪**：同一时间走同一路线的玩家，可以选择跟踪前面的玩家，也可以不跟踪；跟踪者共享路线遭遇与视野。
- **世界时钟**：每日推进一次，怪物强度上升、岛屿出现新事件。

## 4. 三个承重点的设计（本次改进的核心）

### 4.1 海的密度与遭遇

问题：坐标可以随便定、海可以无限大，随机漂流很容易又大又空，十次撞不见一个岛，游戏就死了。

- **有限海域起步**：先开 21×21 格海域，后续按岛屿数量扩展；坐标有边界。
- **出生区**：新玩家出生在中心区域（0,0 附近），出生区 3 格内不允许建岛（防堵门）。
- **岛屿间距**：两岛之间至少间隔 1 格（防重叠）；同一坐标只能有一座岛。
- **洋流**：每天一条洋流方向，沿洋流移动不消耗体力（或更快）；洋流方向指向岛屿较多的区域，把人往有内容的地方推。
- **热门坐标**：显示“最近有人活动的海域方向”（只给方向提示，不透露精确坐标）。
- **遭遇概率目标**：随机漂流 5 步内至少撞见一座岛的概率 ≥ 50%（数值待模拟验证）。
- **岛屿沉没**：长期无人访问的岛进入沉没候选（先警告岛主，超时无访问则沉没并释放坐标），保持海图新鲜。

### 4.2 数字系统与裁决

问题：纯文字最容易“口胡”（“我一刀砍死所有怪”）；怪物变强、升级船只都需要可裁决的数字。

原则：**AI 负责讲故事，数字负责裁决**；自由发挥不能推翻数字。

- **船**：耐久、速度、货仓、武器（数值）；升级 = 消耗资源提升数值。
- **玩家**：血量、体力（移动 / 行动消耗）、背包（物品 + 数量）。
- **怪物**：强度（随世界时钟增长）、数量；遭遇时生成遭遇数值。
- **资源**：统一资源种类（燃料、零件、食物、建材、科技件），岛屿按资源方向产出对应资源。
- **物品**：统一物品表，物品带标签（燃料 / 零件 / 武器 / 药品 / 科技），效果由标签决定，不逐物写逻辑。
  - 例如汽车只有三种状态：报废的（能抽汽油、能拆零件）、能开的（要油，可能缺零件）、锁住的（要工具开）——一张数据表，不是一辆车一份代码。
  - 科研仪器同理：先只有几类原型（供能 / 扫描 / 制造 / 医疗），每台带完好度（好的 / 坏的 / 缺件）；维修是一条通用规则（坏的东西 + 对应零件 + 时间 = 修好）。
- **行动裁决流程**：玩家用文字描述行动 → 系统提取意图 → 按数字规则判定（成功 / 失败 / 消耗）→ AI 按判定结果叙述。判定失败时 AI 不得改写结果。
- **战斗**：回合制数值对抗（攻击 / 防御 / 血量），AI 只负责叙述战况。
- **岛屿规则**：岛主的自然语言规则由 AI 解释，但不得与全局数字规则冲突（冲突时全局规则优先）；规则需经 AI 检查通过才能生效（防“本岛无敌”类规则）。

### 4.3 AI 成本与路由

问题：每个动作都过一次模型，量起来很贵。

- **分层调用**：日常航行描述、进岛描述、闲聊叙述 → 便宜模型（L0/L1）；关键裁决（战斗结果、稀有掉落、岛屿规则解释）→ 较好的模型（L2）；世界演变（每日一次）→ 批量处理。
- **模板化叙述**：高频场景（航行、空海、常见遭遇）先用模板 + 少量模型润色，减少调用。
- **缓存**：同一岛屿的描述、同一怪物的叙述可复用 / 微调，不每次都重新生成。
- **成本上限**：每玩家每日 AI 调用预算（可配置）；超预算后降级为模板叙述。
- **复用已有思路**：英语平台的路由设计（Router 选模型、Gateway 只负责调用、成本与配额管理）可直接复用。

## 5. 最小版本（MVP）范围

- 网页聊天室（公共海频道 + 岛屿子频道）
- 坐标海（有限海域、出生区、移动 / 随机漂流）
- 造岛（名字、坐标、3–5 条规则、资源方向）
- 遭遇与探索（进岛、收集、简单战斗）
- 船只升级（数值）
- AI 叙述 + 数字裁决
- 每日世界推进（怪物增强、岛屿事件）
- 不做：PvP、交易、付费、3D / 画面、手机 App（先 Web）

## 6. 技术选型（建议）

- 后端：TypeScript + NestJS 模块化单体（复用英语平台经验），PostgreSQL（世界 / 岛屿 / 玩家状态）+ Redis（在线状态、频道、移动节流）。
- 前端：Web 聊天室（先 Web，验证玩法后再考虑 App / 小程序）。
- 实时：WebSocket（频道消息、移动、遭遇推送）。
- AI：LLM 路由（复用 L0–L3 路由思路），世界演变用定时任务。
- 部署：现有新加坡服务器可复用。

## 7. 路线图（草案）

- M0：设计定稿（本文档）、数据模型与接口定义。
- M1：原型——聊天室 + 坐标海 + 移动 + AI 叙述（单岛、单人可玩）。
- M2：岛屿创建与规则、收集与战斗裁决、船只升级。
- M3：世界演变时钟、跟踪与多人同路线、岛屿子频道。
- M4：激励与治理（岛屿评分、沉没机制、创作者激励）、商业化探讨。

## 8. 待讨论问题（open questions）

- PvP：是否允许抢岛 / 攻击其他玩家？默认建议 MVP 不做。
- 交易：玩家之间能否交易资源？船只之间能否补给？
- 岛屿审核：规则由 AI 检查，尺度怎么定？是否需要人工复核？
- 货币与变现：先不做；后续考虑岛屿赞助 / 创作者激励（参考蛋仔模式）。
- 坐标海大小与扩展节奏：初始 21×21 是否合适？
- 移动消耗：移动是否消耗体力 / 时间？每天行动次数上限？
- 怪物主动攻击：怪物是否会离开岛屿追到海上？什么条件下攻击玩家？
- 死亡惩罚：死后掉落什么？回出生点还是留在原地？
- 名字：drift-islands 只是工作名，正式名待定。
